2. GLITCH NO EIXO ("000000") — SLA4 em modo escuro
------------------------------------------------------
- Causa: quando todos os valores do período são 0 (ex: SLA4 sem quebras),
  o MUI X calcula uma escala de eixo degenerada (min=max=0) e chega a
  desenhar vários ticks "0" sobrepostos — mais os rótulos de valor de
  cada barra (`barLabel`), também "0", sobrepostos no mesmo ponto. Some
  tudo isso no mesmo pixel e lê-se "000000".
- Corrigido em TrendChart.jsx e PriorityBarChartMui.jsx:
  - Eixo Y ganha um teto mínimo (`max: 1`) só quando TODOS os valores do
    gráfico são zero — evita a escala degenerada sem alterar o
    comportamento quando há dados reais.
  - `barLabel` passou a devolver string vazia para valores 0 (não mostra
    "0" repetido em cada barra vazia).

- frontend/src/components/Charts/PriorityBarChartMui.jsx: mesma
  correção — `barLabel="value"` como prop do `<BarChart>`.
- Confirmado com `grep` nos `.d.ts` do pacote instalado
  (node_modules/@mui/x-charts) que `arcLabel`/`arcLabelMinAngle` do
  ToolsPieChartMui.jsx ESTAVAM certos desde o início (esses sim são
  campos válidos de cada série de pie chart) — por isso as percentagens
  nas fatias já funcionavam.
- ToolsPieChartMui.jsx: legenda voltou pro lado direito (revertida a

ALTERAÇÕES FS — 2026-08-04 (continuação 4, mesmo dia)
============================================================

Pedido: o valor por cima da barra (já a funcionar, centrado dentro
dela) devia ficar no TOPO da barra, não no meio — como no exemplo do
dashboard antigo (Power BI).

Investigação (com Node.js disponível, fui direto ao código-fonte
instalado em vez de adivinhar): o `barLabel` embutido do MUI X Charts
não tem NENHUMA opção de posição — confirmado em
BarChart/BarLabel/BarLabelPlot.js que a coordenada é sempre calculada
como o centro exato da barra (`x + width/2, y + height/2`), sem prop
pública pra mudar isso. Perguntei ao utilizador se queria mesmo assim
avançar sabendo que não consigo testar visualmente o alinhamento —
respondeu que sim.

Solução: nova função de rótulos, independente do `barLabel` embutido.
- frontend/src/components/Charts/BarValueLabels.jsx (novo): recebe os
  mesmos `data`/`series` já passados ao gráfico e desenha o próprio
  `<text>` SVG por cima de cada barra, usando os hooks públicos

ALTERAÇÕES FS — 2026-08-05 (continuação) — Otimização geral (backend + frontend)

Pedido: "vamos otimizar e melhorar o codigo... tornar a app mais rapida

--- Achado principal: cálculo morto a correr a cada ciclo do scheduler ---

backend/cache.py: _compute_derived_cache() rodava a CADA ciclo (a cada

servidor) um pipeline completo — enrich_sys_report_template() (todas as
transformações linha a linha) + ~12 funções de métricas (kpis,
priority_breakdown, tools_breakdown, incidents_summary, operators_
summary, quality_metrics, aioper_summary, sem_evento_summary, sla_
overview, sla3/sla4_detailed) — só pra guardar tudo isso em CACHE.

Investigação (grep de "CACHE[" e "CACHE.get" em todo o backend/
routers): NENHUM endpoint lê mais essas chaves de CACHE. Confirmado
ficheiro a ficheiro — dashboard.py, sla.py, incidents.py, operators.py
e a maior parte de analytics.py já tinham migrado pra ler do histórico
no SQLite (history_service.py) numa passagem anterior desta sessão. Só
backlog_summary/despromovidos_summary (analytics.py) ainda liam de
CACHE — e essas tabelas (mon_backlog_incs/ritm, despromovidos) estão
desativadas há tempos (comentadas em cache.py, sem link configurado),
então nunca chegavam a dfs mesmo assim: davam sempre erro de qualquer
forma. Ou seja: _compute_derived_cache() inteiro rodava pra ninguém.

Corrigido: refresh_all() agora só faz o que interessa de verdade —
baixar (fetch_and_download_csvs) + gravar no SQLite
(_store_and_clean_csvs), que é o que o history_service.py de facto
lê em cada pedido da API. _compute_derived_cache() removido, junto
com os imports que só ele usava (dashboard_service, incidents_service,
operators_service, sla_service, enrich_sys_report_template,
exclude_hidden_technicians, exclude_canceled_incidents — todos ainda
usados noutros ficheiros, só não em cache.py). Erros fixos pra
backlog/despromovidos (tabelas desativadas) substituem o cálculo que já
falhava sempre. Sem mudança de comportamento pra ninguém: as 2 chaves
que ainda eram lidas (/analytics/backlog, /analytics/despromovidos)
já devolviam 503 antes desta mudança, continuam a devolver 503 agora,
só que sem gastar CPU/memória a tentar calcular o resto primeiro.

--- transform.py: vetorização + remoção de coluna morta ---

enrich_sys_report_template() corre a CADA pedido (não só no ciclo do
scheduler) — toda vez que alguém abre Visão Geral, Central Operacional,
Report SLAs ou AIOPER. Tinha 5 passagens df.apply(axis=1) (uma função
Python por linha, lenta em dataframes de milhares de linhas):

1. add_turno_column (coluna "Turno") — CONFIRMADO (grep) que nada
   downstream nunca leu essa coluna desde a migração 2026-08 (a lista de
   técnicos TECNICOS_BR/TECNICOS_PT também já estava desatualizada, com
   nomes de uma equipa antiga). Removida por completo — função,
   constantes e a chamada dentro do pipeline. Elimina uma passagem
   .apply() inteira que só produzia um dado descartado.
2. add_region_column — vetorizada (Series.str.contains + np.where em
   vez de função por linha). Mesmo resultado, ~100x mais rápido nessa
   passagem isolada (é operação C-level do pandas/numpy em vez de
   chamar Python linha a linha).
3. add_grupo_column — vetorizada (Series booleanas + np.select),
   preservando exatamente a mesma prioridade AIOPER > Monitorização >
   Operação do if/elif original (inclusive o detalhe de
   MONITORIZACAO_NOMES comparar com o nome tal como veio, não
   maiúsculas — preservado de propósito).
4. _event_id (usado por keyword_found e source dentro de
   add_keyword_columns) — recalculava a mesma string de correlation_id+
   correlation_display DUAS VEZES por linha (uma em cada apply). Agora
   _event_id_series() calcula uma vez só (vetorizado) antes dos dois
   applies, que passaram a ler o valor já pronto numa coluna temporária
   (removida no fim). add_keyword_columns em si (a lógica de match
   contra KEYWORD_LIST) ficou como estava — vetorizar isso teria mais
   risco de mudar comportamento sutilmente, não valeu o risco nesta
   passagem.

Validação de correção (não só "não deu erro" — output IDÊNTICO):
capturei get_range_summary('2026-07-01','2026-07-31') e
get_monthly_summary('2026-07') completos ANTES de tocar em
transform.py (git stash), depois DEPOIS das mudanças, e fiz diff dos
dois JSONs (ordenados, tudo incluído) — zero diferenças nos dois casos.

Medição real de performance (mesma chamada, git stash/stash pop
pra comparar antes/depois no mesmo dado real, média de 5 chamadas):
get_range_summary('2026-05-01','2026-08-04') (4 meses, a chamada mais

--- Frontend: cache do react-query ---

frontend/src/main.jsx: QueryClient usava as opções default
(staleTime: 0, refetchOnWindowFocus: true) — cada vez que o
utilizador voltava à aba do browser, TODAS as queries ativas refaziam o

4. AUTENTICAÇÃO E AUTORIZAÇÃO (admin vs operador)
-------------------------------------------------------
Pedido do utilizador: "Gestão de Turnos" e "Base de Dados" só
acessíveis a utilizadores específicos, com um controlo de quem é
"admin" e quem é "operador". Contexto obtido por perguntas de
esclarecimento: a app vai ficar num servidor acedida via browser pela
empresa, e a empresa já tem os utilizadores identificados por
"cookies"/credenciais do browser — decidiu-se usar esse mecanismo em
vez de um login com password próprio.

- backend/services/auth_service.py (novo): `get_current_user()` lê o
  username de um cabeçalho de confiança (nome do cabeçalho configurável
  via `AUTH_HEADER_NAME`, default "X-Remote-User") ou, em
  desenvolvimento, de `AUTH_DEV_BYPASS_USER` (só deve existir em
  ambiente local, nunca em produção — documentado explicitamente no
  .env.example e no código). `require_admin()` é uma dependency FastAPI
  (401 sem utilizador identificado, 403 se não for admin) usada nos
  routers protegidos.
- backend/routers/auth.py (novo): GET /api/auth/me (quem sou eu,
  sou admin?).
- backend/routers/turnos.py / backend/routers/db_admin.py:
  `dependencies=[Depends(auth_service.require_admin)]` no
  `APIRouter(...)` — protege TODOS os endpoints do router de uma vez
  (não é preciso decorar cada endpoint individualmente).
- backend/.env: `AUTH_HEADER_NAME=X-Remote-User`,
  `AUTH_DEV_BYPASS_USER` (só localmente).
- Frontend: frontend/src/hooks/useCurrentUser.js (pergunta /auth/me),
  frontend/src/components/RequireAdmin.jsx (bloqueia a rota se não for
  admin — usado a envolver as rotas de Gestão de Turnos/Base de Dados
  em App.jsx), frontend/src/layouts/MainLayout.jsx (esconde os links
  da sidebar para quem não é admin).

AVISO DE SEGURANÇA EXPLÍCITO (documentado no código e reforçado aqui):
este mecanismo confia cegamente no cabeçalho `X-Remote-User` — só é
seguro se o servidor estiver atrás de um proxy que AUTENTIQUE de
verdade o utilizador (Windows Integrated Auth/NTLM/Kerberos) antes de
a app receber o pedido, e que não deixe ninguém definir esse cabeçalho
à mão vindo de fora. Sem esse proxy, qualquer pessoa podia mandar o
cabeçalho que quisesse e fingir ser admin. A esconder os links da
sidebar no frontend NÃO é proteção nenhuma por si só — a proteção real
está nos `require_admin` do backend.

11. REPOSIÇÃO DO CONTROLO DE VERSÕES (GIT)
------------------------------------------------

Ao fechar a revisão da secção 10, o facto de o projeto não ter `.git`
nem testes automatizados foi sinalizado ao utilizador como uma lacuna
de projeto (não só de código) — perguntei se queria que inicializasse
o git. Resposta: "eu fiz download do nosso repositório do git pois
estava com problemas mas o projeto deveria estar ligado a
https://github.com/JadsonCris/GCC-Tools, se conseguires fazer um push
para lá melhor."

Investigação antes de mexer em nada: `git ls-remote` + um clone à parte
(fora da pasta do projeto, só pra inspecionar) confirmaram que o
GitHub AINDA tinha o histórico real (8 commits, o último "Adicionar
Ponto de Situacao, Splunk Validacao e ajustes no CAB") — ou seja, a
pasta local (sem `.git`) e o histórico do GitHub tinham divergido sem
nenhuma relação entre si, e um `git checkout` normal teria sobrescrito
todo o trabalho local acumulado (todas as secções 1-10 desta entrada, e
sessões anteriores) com a versão antiga do GitHub. Reconciliado sem
apagar nada dos dois lados:
1. `git init -b main` + `git remote add origin` + `git fetch origin`.
2. `git update-ref refs/heads/main origin/main` — aponta o branch local
   pro topo do histórico do GitHub SEM tocar em nenhum ficheiro local
   (ao contrário de um `git checkout`, que teria sobrescrito).
3. `git status` a partir daí mostrou a diferença real entre o histórico
   do GitHub e o estado atual da pasta: 27 ficheiros novos, 41
   modificados, 2 removidos (audit_service.py/backlog_service.py, ver
   secção 10b) — exatamente o trabalho acumulado, nada mais.
4. Encontrado de caminho: o repositório do GitHub tinha a pasta
   `venv/` inteira versionada (~194MB, 5258 ficheiros — 100%
   reproduzível via `pip install -r backend/requirements.txt`).
   Perguntado ao utilizador se queria manter essa convenção ou
   descartar — escolheu descartar. `.gitignore` atualizado
   (`venv/` adicionado).
5. Um commit único a consolidar o trabalho acumulado (mensagem
   detalhada a listar as secções 1-10 desta entrada) e
   `git push origin main` — fast-forward normal, SEM `--force`, sem
   reescrever nem apagar nenhum commit existente no GitHub.

Confirmado: `git ls-remote` no GitHub e `git rev-parse HEAD` local
devolvem o mesmo commit depois do push; `git status` local limpo; nenhum
segredo (`.env`, `dashboard.db`, `downloads/`) entrou no commit
(confirmado por grep no diff staged antes de commitar).
